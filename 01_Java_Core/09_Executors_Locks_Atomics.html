What a pool gives you

  • Reuse — no create/destroy cost per task
  • A limit — at most N tasks run at once (protects CPU, DB, the device grid)
  • A queue for the rest, plus lifecycle: shutdown, Futures

Remember: a platform thread is an OS thread — memory for its stack and real creation cost. Separate what runs (a Runnable/Callable) from how it runs (an ExecutorService).

Executors.* traps & clean shutdown

Good to know In Spring use ThreadPoolTaskExecutor (core / max / queueCapacity properties, shuts down with the context). execute() lets an exception kill the worker and print it; submit() stores it in the Future — you only see it via get().

Remember: name your threads, bound your queues, choose a rejection policy, and always shut pools down.

Good to know ReentrantReadWriteLock: many readers or one writer — good for a read-heavy config cache. StampedLock adds optimistic reads (not reentrant). synchronized pinning virtual threads → page 10.

Remember: default to synchronized (simple, can't forget to unlock). Reach for ReentrantLock when you need a timeout, interruptible wait, fairness or several conditions.

2.2

Atomics & compare-and-set

two threads add a passed test to the counter (currently 5)
Good to know Under heavy contention many threads spin on one value — LongAdder spreads counts over cells and sums on read (great for metrics). ABA: a value goes A→B→A and CAS can't tell — AtomicStampedReference adds a version.

Remember: count++ is read-modify-write — three steps, not atomic, even on a volatile. Atomics are lock-free: no blocking, just retry. Combine two atomics and you need a lock again.

3.2

ThreadLocal in a pool

pool threads are reused — so is whatever you left in them
Good to know Same rule for MDC log context (MDC.clear()) and security context. Spring's TaskDecorator copies context into a task and clears it afterwards. Java 25 ScopedValue is the leak-free alternative.

Remember: a ThreadLocal lives as long as the thread, not the task. In a pool, always set at the start and remove() in finally — or the next task inherits the last tenant (and old values never get garbage-collected).
