2. Class loading & Metaspace

2.1

Class loading & Metaspace

before your code runs, its classes must be found and described

The class loader finds .class files (your jar + JDK modules) and stores their metadata in Metaspace.

  • Parent-first delegation — App asks Platform, Platform asks Bootstrap. Core classes like java.lang.String can't be replaced.
  • Load → Link → Init — verify bytecode, give statics default values, run static {} on first use.
  • Metaspace is native memory that grows on demand. PermGen (fixed, inside the heap) was removed in Java 8.
  • Classes unload only with their loader — a leaked ClassLoader keeps every class it loaded alive.
Good to know Static values live with the Class object on the heap; Metaspace holds the class description.

3. Thread stacks

3.1

Thread stacks

every thread has its own — nothing here is shared

Each thread gets a stack (~1 MB, -Xss). A method call pushes a frame; return pops it.

  • A frame holds local variables, the operand stack and the return address.
  • Primitives by value, objects by reference — int retries = 2 sits in the frame; new TestRun() goes to the heap, the frame keeps a pointer.
  • No GC needed — popping frees it instantly, and it's thread-safe by design.
  • PC register per thread = the bytecode it is executing now.
  • Too deep (runaway recursion) → StackOverflowError.
Good to know Virtual threads (Java 21) keep their frames on the heap while parked, so millions fit.

4. Young generation

4.1

Young generation

where every object is born — and most of them die

Most objects die young (a request's DTOs, a step's temp strings), so the heap keeps new objects apart and cleans that area often and cheaply.

  • Eden — every new lands here. Each thread bumps a pointer in its own TLAB: no locks.
  • Young (minor) GC — when Eden fills, copy only the live objects to a survivor and wipe Eden. Cost ∝ live objects, not garbage.
  • S0 / S1 — one is always empty. Survivors bounce between them, age +1 per GC.
  • Promotion — past the age threshold (MaxTenuringThreshold, max 15) or when survivors overflow → Old.

5. Old gen & GC

5.1

Old generation & the garbage collector

long-lived objects, rarer and costlier cleaning

Caches, connection pools and sessions end up in Old. Cleaning it is rarer and more expensive.

  • Reachability — the GC traces from GC roots (stack locals, static fields, JNI). Unreachable = garbage, even objects that point to each other.
  • Stop-the-world — app threads pause for parts of every GC. The goal is short pauses.
  • G1 (default) — heap split into regions; Mixed GCs clean the old regions with the most garbage within a pause goal (200 ms).
  • Full GC = whole heap, long pause → a symptom: leak or heap too small.
Good to know ZGC (-XX:+UseZGC, generational since 21) keeps pauses under ~1 ms even on huge heaps.

6. Off-heap & the pod limit

6.1

Off-heap memory & the container limit

the pod counts the whole process, not just -Xmx

A Java process uses far more than its heap. Kubernetes counts all of it against the pod limit.

  • Native areas — Metaspace, code cache (JIT output), thread stacks, direct buffers (Netty, Mongo driver), GC bookkeeping.
  • Over the limit → the kernel's OOM killer: OOMKilled, exit 137, and no OutOfMemoryError in your logs.
  • Size heap as a % — -XX:MaxRAMPercentage=70 instead of a hard -Xmx; leave ~25–30% for native.
  • Container-aware — the JVM reads the cgroup limit (Java 10+), so the % follows the pod.
