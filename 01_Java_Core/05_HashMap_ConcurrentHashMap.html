1. HashMap inside

1.1

From key to bucket

pick a key and watch the bits
capacity n =
1 · hashkey.hashCode() then spread the high bits down
2 · index(n - 1) & hash — a fast % because n is a power of 2
3 · storeempty → new node, same key → replace value, else append

Remember: the hash picks the bucket, equals() picks the entry inside it. Equal keys must have equal hashCodes, and a key must not change after it is put.

Good to know A null key has hash 0 → always bucket 0. HashMap allows one null key and many null values.

▶ One bucket keeps growing — what happens?

nodes in bucket 9

Remember: resize doubles the table and costs O(n). Each entry either stays at index j or moves to j + oldCap — decided by one bit of the hash, no re-hashing. Trees keep a terrible hashCode() at O(log n) instead of O(n).

Good to know new HashMap<>(100) gives a table of 128 that still resizes at 97 entries. To hold 100 without resizing use HashMap.newHashMap(100) (Java 19+).

Remember: HashMap has no locks. Concurrent writes lose entries, corrupt size(), and a write during resize can hide entries from readers. (Before Java 8 a concurrent resize could even create an infinite loop.)

2.2

How ConcurrentHashMap stays fast (Java 8+)

pick a case to see which lines run

Three rules

  • ⚡ Empty bucket → one CAS, no lock
  • 🔒 Busy bucket → synchronized on its first node only
  • 👁 get() never locks — volatile reads of the table and node values

Remember: no global lock (the Java 7 "16 segments" design is gone). Threads writing to different buckets never wait for each other.
