2. Shared state

2.1

Race condition: the lost update

passed++ is three steps, not one
passed (heap)0expected 2

Remember: a race needs shared + mutable + unsynchronized. Remove any one: don't share (local/ThreadLocal), don't mutate (immutable), or synchronize.

2.2

synchronized — which calls block each other?

pick one call per thread

What it guarantees

  • Mutual exclusion — one thread at a time per lock object
  • Visibility — writes before unlock are seen after the next lock
  • Reentrant — updateStatus() may call addResult() without deadlocking itself
Thread 1 calls
Thread 2 calls

Remember: threads block each other only when they lock the same object. Instance methods lock this, static ones lock the Class — they don't block each other.

Good to know Prefer a private final lock object (synchronized (resultsLock)) and keep the block small — never do I/O (HTTP, DB) while holding a lock.

3. Visibility (JMM)

3.1

volatile: the "Stop run" button

a write in one thread may never be seen by another
main memory
stopRequested = false
worker's view (CPU cache / JIT)
stopRequested = false
worker loop: idle

volatile gives you

  • Visibility — every read goes to the latest write
  • Ordering — no reordering around the volatile access
  • ❌ not atomicity — volatile int count; count++ still loses updates → use AtomicInteger

Remember: use volatile for a flag written by one thread and read by others. For read-modify-write use atomics or locks.
