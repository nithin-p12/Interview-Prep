1. The hierarchy

1.1

Throwable family tree

click any class
Error — unchecked
Exception — checked
RuntimeException — unchecked

Remember: checked = Exception and its subclasses except RuntimeException — the compiler forces you to catch or declare them. Errors mean the JVM is in trouble; don't catch them.

1.2

Checked or unchecked?

classify each one
FileNotFoundException
An IOException — the file may genuinely be missing, so the caller must decide.
NumberFormatException
Extends IllegalArgumentException → RuntimeException.
InterruptedException
Checked — restore the flag with Thread.currentThread().interrupt() if you can't rethrow.
ClassCastException
RuntimeException — a programming bug.
TimeoutException
java.util.concurrent.TimeoutException extends Exception — e.g. future.get(5, SECONDS).
UncheckedIOException
Wraps an IOException in a RuntimeException — handy inside lambdas/streams.
DataAccessException (Spring)
Spring translates checked SQLException into unchecked DataAccessException.
CloneNotSupportedException
Checked — one reason clone() is disliked.

Checked — "you might recover, decide now"

Compiler-enforced. Good when the caller can really act (retry, ask for another file). Painful in lambdas and layered code.

Unchecked — "a bug or an unrecoverable state"

Not enforced. Spring, Hibernate and most modern APIs use them, handled once at the boundary.

Remember: finally runs after return and after an uncaught exception — only System.exit(), a JVM crash or a killed thread skip it. Never return or throw from finally.

2.2

try-with-resources

close order and suppressed exceptions

Why it beats a manual finally

  • Works with anything AutoCloseable (streams, connections, locks you wrap)
  • Closes in reverse order, even when the body throws
  • A failure in close() is suppressed — the original error isn't lost (old finally { close(); } hid it)

Remember: always use try-with-resources for anything you open. Since Java 9 you can also list an existing effectively-final variable: try (conn) { … }.

4. All in action

4.1

Predict the output

finally and catch traps
static int f() {
    try { return 1; }
    finally { return 2; }
}
System.out.println(f());
return in finally overrides the try's return (and would swallow any exception). 2.1
static int f() {
    int x = 1;
    try { return x; }
    finally { x = 5; }
}
The return value 1 is saved before finally runs; changing x afterwards doesn't affect it.
try {
    throw new IllegalStateException("A");
} finally {
    throw new RuntimeException("B");
}
The exception from finally replaces A — the original error is lost. try-with-resources avoids this with suppressed exceptions.
try { readFile(); }
catch (Exception e)   { … }
catch (IOException e) { … }
IOException is already caught by Exception → unreachable catch. Order catches from specific to general.
catch (IOException | SQLException e) {
    e = new IOException("retry");
}
A multi-catch parameter is implicitly final.
try {
    int[] a = new int[Integer.MAX_VALUE];
} catch (Exception e) {
    System.out.println("caught");
}
OutOfMemoryError is an Error, not an Exception — it flies past catch (Exception).
