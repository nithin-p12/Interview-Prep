2

Java Heap

shared by all threads · objects & arrays · G1 splits it into equal-size regions
-Xms-Xmx-XX:G1HeapRegionSize

Example region map — roles are assigned dynamically and change after every GC.

E

Eden regionsmost new objects, allocated via per-thread TLABs (Thread-Local Allocation Buffers)

S

Survivor regionsobjects that survived a Young GC (age + 1) — any free region, not fixed S0/S1 spaces

O

Old regionspromoted once age ≥ tenuring threshold (adaptive, max 15)

H

Humongous regionsobjects ≥ ½ a region, allocated directly into contiguous old regions

Free regionsavailable for any role

Young gen = Eden + Survivor regions. Its size adapts (≈5%–60% of the heap) to meet -XX:MaxGCPauseMillis (default 200 ms) — there is no fixed Eden:Survivor ratio in G1.

Class mirrors (java.lang.Class)

One per loaded class. Holds the static fields. Reachable while its class loader is alive.

Interned String objects

Ordinary heap objects — can sit in Young or Old regions and are collectable. Indexed by the native StringTable.

Virtual-thread stack chunks

When a virtual thread blocks, its frames are copied into heap objects until it resumes.

Object lifecycle in G1

new Object()→TLAB in Eden→Young GC evacuates (copies) live objects→Survivor region, age++→age ≥ threshold → Old region

Humongous objects skip Eden → H regions. Unreachable objects are simply not copied, so their whole region is freed. Still no space → OutOfMemoryError: Java heap space.

Native (non-heap) Memory

outside -Xmx · allocated from the OS

Method Area logical area from the JVM spec — per-class structures; the spec doesn't fix where they live

Metaspace HotSpot's native storage for class metadata-XX:MaxMetaspaceSize

Klass

class metadata · fields, methods · vtables / itables

ConstMethod

method bytecode · line & exception tables

ConstantPool

runtime constant pool, one per class · symbolic refs, literals

MethodData

profiling data & counters used by the JIT
  • Compressed Class Space: Klass structures addressed with 32-bit pointers · -XX:CompressedClassSpaceSize
  • Grows on demand · freed per class loader after its classes are unloaded · OutOfMemoryError: Metaspace
  • Class mirror & static fields are NOT here → Heap

StringTable native hash table

Maps string contents → interned String objects that live in the heap. Filled by string literals and String.intern(). -XX:StringTableSize

Other native memory

  • thread stacks
  • direct ByteBuffers · -XX:MaxDirectMemorySize
  • FFM off-heap MemorySegments (Arena)
  • GC data: remembered sets, card table, mark bitmaps · symbol table
  • track it: -XX:NativeMemoryTracking=summary

Code Cache JIT-compiled native code, segmented layout-XX:ReservedCodeCacheSize

Non-method

interpreter, stubs, adapters, buffers

Profiled

C1 code with profiling (tiers 2 – 3)

Non-profiled

C2 code (tier 4) and trivial C1 code (tier 1)
4

Threads

private per thread · not shared · freed when the method returns / thread ends
-XssStackOverflowError

Platform thread

PC Register

Index of the current bytecode instruction. Undefined while a native method runs.

Thread stack (one native OS stack, LIFO)

Java frame: current() ← top
Local VariablesOperand StackFrame Data
Java frame: caller()
Native frame: C code called via JNI / FFM

Spec: separate JVM Stack + Native Method Stack. HotSpot: both live on one native stack.

Virtual threads

  • lightweight threads scheduled by the JVM
  • run mounted on a carrier platform thread (ForkJoinPool) and use its stack
  • on blocking I/O they unmount: frames move to stack-chunk objects in the heap and the carrier is freed
  • millions possible · ideal for request-per-thread servers
Frame Data = return address, link to the runtime constant pool, exception handling. Local variables hold primitives and object references — the objects themselves live in the heap.

Execution Engine

runs bytecode — interpreted first, compiled when hot

Interpreter template interpreter

  • executes bytecode one instruction at a time
  • fast start-up, slow for hot code
  • counts invocations & loop back-edges
  • fills MethodData profiles
  • deoptimised code resumes here
  • hot method → handed to the JIT

JIT Compiler — tiered compilation

L0Interpretercollects profiles
L1C1, no profilingtrivial methods (getters …)
L2C1, light profilingused when the C2 queue is busy
L3C1, full profilingtypical step before C2
L4C2speculative, highly optimised

Common path 0 → 3 → 4 · trivial methods 0 → 1 · tiers may be skipped · a failed assumption → deoptimise → back to L0

Optimisations

inlining · escape analysis & scalar replacement (no heap allocation) · loop optimisations · intrinsics · dead-code removal

OSR & Code Cache

On-stack replacement swaps a running loop into compiled code. All compiled code goes to the Code Cache.

Garbage Collection — G1

region-based, pause-time goal
-XX:MaxGCPauseMillis=200-XX:InitiatingHeapOccupancyPercent

The G1 cycle

Young GCSTW · evacuate young
→
Concurrent Startpiggybacks a Young GC
→
Concurrent Markapp keeps running
→
RemarkSTW · finish marking
→
CleanupSTW · pick old regions
→
Mixed GCsyoung + some old
↺

Old-gen occupancy ≥ IHOP → marking cycle starts · Mixed GCs reclaim the old regions with the most garbage · then back to young-only.

Full GC — fallback only: stop-the-world compaction of the whole heap when evacuation runs out of space (also unloads classes).

GC Roots

Starting points of reachability — not a GC component:

  • locals & operands in thread stacks
  • JNI global / local references
  • loaded classes → class mirrors → static fields
  • JVM-internal references

Remembered Sets & Write Barriers

  • a post-write barrier dirties a card when a reference is stored
  • each region's remembered set lists incoming cross-region references
  • Young GC scans roots + RSets, not the whole old generation
  • SATB pre-write barrier keeps concurrent marking correct

Reference strength (java.lang.ref)

Not types of roots:

  • Strong — never cleared
  • Soft — cleared under memory pressure
  • Weak — cleared at the next GC
  • Phantom — post-mortem cleanup (Cleaner)
Other collectors: Serial · Parallel · ZGC (generational) · Shenandoah. Epsilon allocates but never reclaims — testing only.

Native Interop

calling C / OS code from Java

JNI — Java Native Interface

C/C++ glue code against JNIEnv · native methods · manual handles & error checks · runs on the calling thread's stack.

FFM API — Foreign Function & Memory

Pure Java: Linker downcalls / upcalls, no glue code · MemorySegment + Arena for safe off-heap memory.

Native libraries

.so (Linux) · .dll (Windows) · .dylib (macOS) — OS calls, file & network I/O, hardware access.

Java 25 HotSpot notes & tools

Worth mentioning

  • Default GC = G1 (Serial on very small machines)
  • ZGC is generational
  • Compact object headers: -XX:+UseCompactObjectHeaders
  • AOT cache for faster start-up: -XX:AOTCache

Inspect a running JVM

  • jcmd <pid> GC.heap_info
  • jcmd <pid> VM.native_memory (needs NMT on)
  • jcmd <pid> Compiler.codecache
  • -Xlog:gc* for GC logs
  • Errors: OutOfMemoryError (heap / Metaspace / direct buffer / native thread) · StackOverflowError
