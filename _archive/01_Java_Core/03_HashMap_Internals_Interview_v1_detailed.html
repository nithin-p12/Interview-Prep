HashMap — Internal Working

Single-threaded view · no locking yet

An array of buckets. Each bucket holds a chain of Nodes (a linked list), which turns into a red-black tree when it gets too long. Everything hinges on hashCode(), equals() and the bucket index.

Must knowThe structure: table → bucket → Node

Mental model

A HashMap is a Node[] table (the buckets). Default length is 16 and it is always a power of 2. Each slot is either null (empty bucket) or points to the first Node of a chain. Every Node stores hash, key, value, next. Two keys that land in the same slot are a collision — they are linked via next.

Ask the key for its hash.

"apple".hashCode() = 93029210
2Spread the bits

Mix high 16 bits into low 16 bits.

3Bucket index

Keep only the low bits (fast modulo).

(16 - 1) & 93030097 = …0001 → 1
4Look at table[1]

Empty → put a new Node there. Not empty → walk the chain: same hash and equals() → replace value; reach the end → append at tail.

5Bookkeeping

modCount++, size++. If chain > 8 → treeify. If size > threshold → resize (double).

hash() and index

Why must capacity be a power of 2?

n - 1 is then all 1s in binary (15 = 1111), so hash & (n-1) = the low bits = a perfect, uniform modulo. new HashMap<>(20) is silently rounded up to 32 by tableSizeFor().

Interview questions
  • Q. Why compare hash first, then equals()?Comparing two ints is cheap; equals() may be expensive. Different hashes ⇒ definitely different keys, so equals() runs only when hashes match.
  • Q. What does put() return?The previous value for that key, or null if it was absent (or was mapped to null).
  • Q. Where does a null key go?hash(null) = 0 → bucket 0. HashMap allows one null key and any number of null values.
  • Q. Is the table created in the constructor?No. new HashMap<>() only sets the load factor; the array is allocated by resize() on the first put.

Must knowCollision & get(key)

What is a collision?

Two different keys end up at the same bucket index. There are two flavours: (a) same hashCode — e.g. "Aa" and "BB" both have hashCode 2112; (b) different hashCode, same index — "apple" and "cherry" have different hashes but both end in binary …0001, so & 15 gives bucket 1 for both. HashMap resolves it with separate chaining: the new Node is linked to the tail of the bucket's list.

Interview questions
  • Q. Java 7 vs Java 8 insertion into a bucket?Java 7 inserted at the head; during a concurrent resize this could reverse links and create a cycle → get() looped forever. Java 8 appends at the tail and keeps order on resize.
  • Q. What if hashCode() returns a constant?Every key goes to one bucket → it becomes a tree (if keys are Comparable, lookups stay O(log n)); otherwise effectively a slow scan. Still correct, just slow.

Must knowLoad factor, threshold & resize

The rule

threshold = capacity × loadFactor = 16 × 0.75 = 12. When ++size > threshold (i.e. the 13th entry), the table doubles to 32 and the new threshold is 24. More buckets ⇒ shorter chains ⇒ lookups stay O(1). 0.75 is the trade-off between memory (empty buckets) and speed (collisions).

Visual — resize 16 → 32 (no rehash: each node stays at j or moves to j + 16)
The split trick
Points to remember
  • Resize is O(n) — every entry is visited. If you know the size, pre-size: new HashMap<>(expected / 0.75f + 1) or Java 19+ HashMap.newHashMap(expected).
  • The hash is cached in the Node, so hashCode() is not called again.
  • Capacity only grows; removing entries never shrinks the table.
  • A higher load factor (e.g. 1.0) saves memory but means longer chains; a lower one (0.5) wastes memory but is faster.
  • A tree bin is split the same way; each half with ≤ 6 nodes is turned back into a list (untreeify).

Must knowTreeification & untreeification (Java 8+)

Why

With bad hashes (or an attacker sending many colliding keys — "hash flooding") one bucket's list could hold thousands of nodes → get() becomes O(n). Java 8 converts a long bucket into a red-black tree (TreeNode) → O(log n). Trees use ~2× the memory of plain Nodes, so it only happens when really needed.

Interview questions
  • Q. Bucket has 9 nodes but table is 16. Tree?No. treeifyBin sees capacity < 64 and calls resize(). Only at capacity ≥ 64 does the bucket become a tree.
  • Q. Do keys need to be Comparable for a tree?No. Order is hash first, then compareTo if the class is Comparable, else tieBreakOrder (class name + identityHashCode). Comparable keys make tree lookups much faster.

Good to knowMore interview questions

  • Q. Is HashMap ordered?No. Iteration follows bucket order, which changes after a resize. Use LinkedHashMap (insertion/access order) or TreeMap (sorted).
  • Q. What is fail-fast?Iterators remember modCount. If the map is structurally modified (not through the iterator) during iteration → ConcurrentModificationException. Best-effort, not a thread-safety guarantee.
  • Q. Time complexity?get/put/remove: O(1) average; worst O(log n) with tree bins (O(n) for a list bin before treeify). Iteration: O(capacity + size).
  • Q. Can I use a mutable object as key?Technically yes, but if a field used in hashCode() changes after insertion, the entry sits in the wrong bucket and can't be found. Use immutable keys.
  • Q. Why is HashMap not thread-safe?No synchronization at all: concurrent puts can overwrite each other's nodes, size loses updates, and a resize can expose half-moved buckets. → see ConcurrentHashMap.
  • Q. HashMap vs Hashtable?Hashtable is legacy: every method synchronized, no null key/value, no treeify, index = (hash & 0x7FFFFFFF) % n. Don't use it in new code.

ConcurrentHashMap

Java 8+ · CAS + per-bucket locks · lock-free reads

Same table / bucket / Node / tree design as HashMap — but writers lock only the head node of one bucket, empty buckets are filled with CAS (no lock at all), and reads never lock.

Must knowThe problem: HashMap under multiple threads

✗ Plain HashMap shared by threads
✓ The two fixes

Collections.synchronizedMap(map)

One lock around every method — correct but only one thread at a time, even for reads. (Page 3)

ConcurrentHashMap

Lock as little as possible: CAS for empty buckets, synchronized(headNode) for one bucket, volatile reads for get(). Threads touching different buckets never wait for each other.

Rule of thumb

Locks are needed to stop two writers corrupting the same chain. Readers don't change anything, so they only need to see a consistent view — volatile gives that.

Must knowput(): CAS on empty bucket, lock on head node otherwise

Visual — 4 threads working at the same time
putVal (simplified from JDK 8+)
What each branch means
  • Empty bucket → CAS (compare-and-swap): "set tab[i] to my node only if it is still null". One CPU instruction, no lock. If another thread won the race, CAS fails and the loop retries — now the bucket is non-empty, so it takes the lock path.
  • Non-empty bucket → synchronized(f) where f is the first node of that bucket. The lock covers just that one chain/tree. 2 threads on bucket 3 → one waits. Threads on bucket 3 and 10 → both run.
  • Re-check tabAt(tab,i) == f after locking: the head might have changed (removed, treeified, resized) while we waited — if so, retry.
  • MOVED (hash = −1, a ForwardingNode): this bucket was already copied to the new table during a resize → the writer helps resizing instead of waiting.
  • Tree bins: the head is a TreeBin object (hash = −2); writers lock it the same way.
  • Before Java 8: Segment locking — 16 Segments (each a ReentrantLock + its own table). Max 16 concurrent writers. Java 8 removed segments; the concurrencyLevel argument is now just a sizing hint.

Must knowget(): reads are freely allowed — no lock

A reader never takes a lock, never does CAS, and is never blocked by a writer — even one holding the lock on the same bucket. Correctness comes from volatile: the table slots are read with tabAt() (a volatile read), and Node.val / Node.next are volatile. A reader sees either the old value or the new one, never a half-built node.

get (simplified)
Details interviewers like
  • Read during resize: if the bucket holds a ForwardingNode, find() follows it into the new table. Readers never wait for a resize.
  • Read on a tree bin: TreeBin has a tiny read/write state (lockState). If a writer is restructuring the tree, the reader simply walks the bin as a linked list (via next) instead of the tree — slower, but never blocks.
  • Weakly consistent: get() reflects the most recently completed update. Iterators never throw ConcurrentModificationException; they may or may not show changes made after they were created.
  • size() is an estimate under concurrency: baseCount + CounterCell[] (same idea as LongAdder, so threads don't fight over one counter). Prefer mappingCount() (returns long).

Must knowResize: many threads help, ForwardingNode marks progress

  • Triggered in addCount() when size reaches sizeCtl (0.75 × n).
  • The table is split into strides (≥ 16 buckets). Each thread claims a stride and moves those buckets — locking each bucket's head while copying.
  • A moved bucket is replaced in the old table by a ForwardingNode (hash MOVED = −1) pointing to the new table.
  • Writer hits a ForwardingNode → helpTransfer(): joins the copy work instead of blocking.
  • Reader hits a ForwardingNode → looks up the key in the new table.
  • Same lo/hi split as HashMap: a node stays at i or moves to i + n.

Must knowCompound operations & no nulls

✗ Check-then-act with separate calls
✓ Use the atomic per-key methods
Interview questions
  • Q. Why are null keys/values not allowed?Ambiguity: get(k) == null could mean "absent" or "mapped to null". In a single thread you'd check containsKey, but concurrently the map can change between the two calls, so the answer is unreliable. Doug Lea banned null to remove the ambiguity.
  • Q. Does ConcurrentHashMap lock the whole map ever?No normal operation does. clear() and resize go bucket by bucket. Only initTable uses a CAS flag on sizeCtl.
  • Q. Why synchronized and not ReentrantLock in Java 8?A lock per bucket must be tiny. Using the existing head node's monitor costs no extra objects, and the JVM optimises uncontended synchronized well.
  • Q. Can two threads write at the same time?Yes — if they hit different buckets. Theoretical max parallel writers = number of buckets.

Collections.synchronizedMap

One lock for the entire map

A thin wrapper around any Map. Every method does synchronized (mutex) { m.method(...) }. The internals of the wrapped HashMap are unchanged — it just lets one thread in at a time, readers included.

Must knowHow it works

Visual — the whole table sits behind one lock
java.util.Collections (simplified)
Consequences
  • Every call — get, put, size, containsKey — acquires the same lock. Two readers block each other.
  • A writer on bucket 3 blocks a reader on bucket 12, even though they touch unrelated data.
  • A resize of the inner HashMap happens while the lock is held → all threads wait for the whole O(n) copy.
  • Each single method is atomic, so the map is never corrupted — but throughput collapses as threads increase.
  • null keys/values are allowed if the wrapped map allows them (HashMap: yes).
  • Works with any Map: synchronizedMap(new TreeMap<>()) keeps sorted order, LinkedHashMap keeps insertion order. Also Collections.synchronizedSortedMap / synchronizedNavigableMap.
  • Hashtable works the same way (methods are synchronized on this), but forbids nulls and is legacy.

Must knowIteration and compound actions need manual locking

✗ Unsynchronized iteration / check-then-act
✓ Hold the map's own lock for the whole sequence
Interview questions
  • Q. Why lock on m and not some other object?The wrapper uses mutex = this. Locking on any other object would not exclude the map's own methods. (If created via the package-private constructor with a custom mutex, use that.)
  • Q. When is synchronizedMap still a good choice?Low contention, need to wrap a TreeMap/LinkedHashMap, need null values, or need to lock a multi-step sequence (iteration + updates) as one unit.

No locks. Two writers in bucket 3 can corrupt the chain.

🔒 only on the head node being written. 👁 readers pass everywhere.

Good to knowQuick-fire interview answers

  • Q. Explain HashMap internal working in 30 seconds.Array of buckets (power of 2). hash = h ^ (h>>>16), index = hash & (n-1). Empty → new Node; else walk chain using hash + equals() → replace or append at tail. Chain > 8 and table ≥ 64 → red-black tree; ≤ 6 → list. size > 0.75n → double and split each bucket into lo/hi.
  • Q. Explain ConcurrentHashMap in 30 seconds.Same structure. Empty bucket → CAS. Otherwise synchronized on the bucket's first node. get() uses volatile reads, no lock. Resize is shared between threads using ForwardingNodes. Size via striped counters. No nulls.
  • Q. Java 7 vs Java 8 ConcurrentHashMap?7: array of 16 Segments (each a ReentrantLock with its own table) → max 16 writers. 8: no segments, lock per bucket + CAS, treeify, cooperative resize, LongAdder-style counting.
  • Q. Is Collections.synchronizedMap(new ConcurrentHashMap()) useful?No — it just adds a global lock and removes CHM's concurrency.
  • Q. Is ConcurrentHashMap "fully" thread-safe for my logic?Only per operation. if (!containsKey) put is still a race — use putIfAbsent / computeIfAbsent / merge.
  • Q. Hashtable vs synchronizedMap vs CHM?Hashtable and synchronizedMap: one lock for everything (Hashtable also bans nulls, legacy). CHM: fine-grained, lock-free reads → preferred.
