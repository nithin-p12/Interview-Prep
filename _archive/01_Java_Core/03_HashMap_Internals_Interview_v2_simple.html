HashMap, ConcurrentHashMap & synchronizedMap

Learn it visually — short explanations, pictures and two playgrounds. No JDK source code needed.

★ Start here 1. HashMap ▶ HashMap playground 2. ConcurrentHashMap 3. synchronizedMap 4. Comparison

Start hereIf you remember only 5 things

  1. HashMap = an array of buckets. The key's hashCode() decides which bucket an entry goes into.
  2. Two keys in one bucket = collision. They form a small linked list. If one bucket gets very long (> 8) it becomes a tree.
  3. When the map is 75% full, the array doubles (resize) so buckets stay short and lookups stay fast.
  4. Keys need correct equals() + hashCode() and should not change after you put them in.
  5. HashMap is not thread-safe. synchronizedMap puts one lock on everything; ConcurrentHashMap locks only one bucket and reads never lock.

HashMap — how it works

single thread

Must knowHow HashMap stores data

Think of a row of 16 numbered boxes (buckets). Each entry (key + value) is stored in one box. Which box? Java takes the key's hashCode() and turns it into a box number. An empty box is null; a box with several entries keeps them in a small chain.

Must knowput() and get() in 3 steps

Example: map.put("apple", 10)
1Get the hash

Call "apple".hashCode() → a big number.

2Pick the bucket

Turn the hash into 0 … 15. For "apple" → bucket 1.

index = hash & (16 - 1)
3Store it

Empty bucket → add. Same key already there → replace the value. Different key → add to the end of the chain.

get("apple") does steps 1 and 2 the same way, then walks the chain in bucket 1 and returns the value whose key equals("apple"). Usually the chain has 0–1 entries, so get/put are O(1).

Interview questions
  • Q. Why check the hash first, then equals()?Comparing two numbers is cheap; equals() can be slow. Different hash = different key, so equals() runs only when hashes match.
  • Q. Where does a null key go?Its hash is 0, so always bucket 0. HashMap allows one null key and many null values.

Must knowCollisions & the equals / hashCode rule

A collision is two different keys landing in the same bucket. That's normal — they are simply chained. Example: "Aa" and "BB" have the same hashCode (2112), so they share a bucket and equals() tells them apart.

Remember: override equals() and hashCode() together, and never change a key after putting it in.

Must knowResize — when the map gets 75% full

Load factor 0.75 means: with 16 buckets, the map resizes when it gets its 13th entry (16 × 0.75 = 12). It creates 32 buckets and moves every entry. Each entry either stays in the same bucket number or moves to number + 16 — no full re-hash needed.

Remember: resize doubles the array and costs O(n). If you know the size up front, create the map with enough capacity.

Must knowTreeify — when one bucket gets too long (Java 8+)

With a bad hashCode() many keys can pile into one bucket, and a long chain makes get() slow (O(n)). So when a bucket has more than 8 entries and the table has at least 64 buckets, Java turns that bucket into a red-black tree → O(log n). If the table is smaller than 64, it just resizes instead. When the bucket shrinks to 6 or fewer, it goes back to a list.

Remember: 8 → tree, 6 → back to list, only if the table has ≥ 64 buckets. Trees are a safety net for bad hash codes, not the normal case.

Good to knowQuick interview questions

  • Q. Is HashMap ordered?No. Use LinkedHashMap for insertion order or TreeMap for sorted keys.
  • Q. Time complexity?get / put / remove are O(1) on average. Worst case O(log n) once a bucket is a tree.
  • Q. What is fail-fast?If the map changes while you iterate (not via the iterator), you get ConcurrentModificationException.
  • Q. HashMap vs Hashtable?Hashtable is old: every method synchronized and no nulls. Use HashMap, or ConcurrentHashMap for threads.

ConcurrentHashMap

safe for many threads, still fast

Must knowWhy plain HashMap breaks with threads

1T1 looks

Bucket 5 is empty.

2T2 looks

Bucket 5 is still empty.

3T1 writes

Puts its entry in bucket 5.

4T2 writes

Overwrites bucket 5 → T1's entry is lost.

Other symptoms: wrong size(), get() missing entries during a resize, and ConcurrentModificationException while iterating. The fix is locking — the question is how much to lock.

Must knowHow ConcurrentHashMap stays fast

⚡ Empty bucket → no lock

Uses CAS (compare-and-swap): "put my entry here only if it is still empty". If another thread was faster, just try again.

🔒 Busy bucket → lock that bucket only

Locks the first node of that one bucket. Threads writing to different buckets never wait for each other.

👁 Reads → never lock

get() uses volatile reads, so it always sees a complete value — even while a writer holds that bucket's lock.
Picture — several threads at the same moment

Remember: CAS for empty buckets, lock one bucket otherwise, reads never lock. No null keys or values allowed.

Must knowUse the atomic methods

Each single call is thread-safe, but two calls in a row are not. Another thread can sneak in between them.

Good to knowQuick interview questions

  • Q. Why no null keys or values?get(k) == null would be ambiguous: missing, or mapped to null? With threads you can't safely check again, so nulls are banned.
  • Q. Can two threads write at the same time?Yes, if they write to different buckets.
  • Q. What about resize?Threads help move buckets to the new table instead of waiting; reads keep working during it.
  • Q. Java 7 vs Java 8?Java 7 used 16 "segments" (max 16 writers). Java 8 locks per bucket + CAS, so it scales much better.

Collections.synchronizedMap

one lock for the entire map

Must knowHow it works

It wraps a normal map and puts one lock around every method — get, put, size, everything. So only one thread at a time can use the map, readers included. Simple and correct, but slow when many threads share it.

Create & use
When to still use it
  • Few threads, little contention.
  • You need null keys or values.
  • You want to wrap a TreeMap (sorted) or LinkedHashMap (ordered).
  • You need several operations to run as one unit using synchronized (m) { … }.

Must knowLocking at a glance

HashMap

No locks. Two writers in bucket 3 can corrupt it.

🔒 around everything. Readers wait in the queue too.

Good to knowSay it in 30 seconds

  • Q. Explain HashMap.An array of buckets. hashCode picks the bucket; equals finds the key inside it. Collisions form a list, which becomes a tree after 8. At 75% full the array doubles.
  • Q. Explain ConcurrentHashMap.Same structure, but an empty bucket is filled with CAS, a busy bucket is locked on its first node, and reads never lock. No nulls.
  • Q. Explain synchronizedMap.A wrapper with one lock around every method. Always correct, but only one thread at a time.
  • Q. Is ConcurrentHashMap enough for my logic?Only per call. For "check then put" or "read then update" use putIfAbsent, computeIfAbsent or merge.
