Login & tenant routing

how a request reaches the right customer's data
  1. Login: the portal sends the user to Keycloak (OAuth2 / OpenID Connect) and gets back a signed JWT with user, roles and license id.
  2. Every API call carries Authorization: Bearer <JWT>. Spring Security in each service checks the signature (Keycloak's public keys), expiry and roles.
  3. The service reads the license id, looks up that license's database in the Auth DB, and then reads / writes only that License DB — tenant isolation.

Data & storage

MongoDB — database per license

  • Auth DB (shared): licenses, plans, users, roles, license → database mapping
  • License DBs (one per customer): projects, scripts, suites, test data, results, history
  • Why: strong isolation, per-customer backup / restore / deletion, no noisy neighbours

Elasticsearch

  • Logs & debugging: centralised service and execution logs — trace one failed run across services
  • Search & filter APIs: full-text search on scripts, elements and results; fast filters, aggregations, pagination

File / artifact storage

  • AWS S3 for cloud deployments (SDK 1.12.797)
  • Server disk for on-prem — same storage API, switched by config
  • Holds screenshots, videos, reports, uploaded test data & app files
  • Old files removed by the Scheduler's retention cleanup

Interview talking points

short answers you can say out loud
Why microservices here?Execution Client and Results scale with test load; authoring doesn't. Separate services let us scale, deploy and fail independently.
Why Kafka between the execution services?Step results arrive in bursts. Kafka buffers them, decouples producers from consumers, allows replay, and consumers scale by partitions.
Why a database per license?Hard tenant isolation, easy per-customer backup / restore / deletion, no index contention. Trade-off: many databases to manage and migrations run per DB.
How does a request find the right database?License id from the JWT → Auth DB lookup → a Mongo template for that license's database.
How do you avoid losing or duplicating results?Kafka is at-least-once, so consumers are idempotent (dedupe by result id). Failed messages retry, then go to a dead-letter topic. Sync calls use Resilience4j.
Cloud vs on-prem?Same Docker images (JDK 25 base). Storage is switched by config: S3 in the cloud, server disk on-prem.
Why Elasticsearch as well as MongoDB?Mongo is the system of record. ES gives fast full-text search, filters and aggregations, plus one place to search logs across services.
How is old data cleaned up?The Scheduler runs retention jobs per license: results, logs and files older than the configured period are deleted from MongoDB, Elasticsearch and S3 / disk.

These describe the intended design. Check exact details (topic names, retry settings) in the code before quoting them.
