Areas
5

runtime data areas — 2 shared, 2 per thread, 1 native

Five areas to name

  • Heap — all objects, shared, garbage-collected
  • Metaspace — class metadata, shared, native memory
  • Stack — one per thread, method frames
  • PC register — one per thread, current instruction
  • Native — code cache, direct buffers, thread stacks themselves
Heap and Metaspace are shared by all threads; each thread gets its own stack and PC register.
Heap
2 gens

young (Eden + 2 survivors) and old

Why two generations?

Most objects die young — a request DTO, a step result being mapped. Collecting the small young space often is cheap; the few survivors are promoted to the old generation, which is collected rarely.

The heap is split by object age because most objects die young — it lets the GC do frequent, cheap minor collections.
Threads
1 : 1

one thread = one stack (≈1 MB, -Xss)

Every thread owns a stack

A stack holds one frame per method call: local variables, references and partial results. It's freed automatically when the method returns — no GC involved. 500 threads ≈ 500 MB of stack memory outside the heap.

Stacks are per thread and never garbage-collected — frames are popped on return. That's why too many threads can exhaust memory even when the heap is fine.

Parallel suite execution with 200 threads reserves ~200 MB of stacks before a single test runs.

Java 8
PermGen → Metaspace

class metadata moved off the heap

PermGen is gone

Before Java 8, class metadata lived in a fixed-size PermGen inside the heap — hot redeploys famously hit PermGen space. Java 8 moved it to Metaspace in native memory, which grows on demand.

Java 8 replaced PermGen with Metaspace in native memory. It grows automatically, so I still cap it with MaxMetaspaceSize to catch classloader leaks early.

Heap = young + old

  • Young: Eden (new objects) + two survivor spaces (objects that survived a GC)
  • Old: objects that survived several young GCs
  • Shared by all threads → objects here need synchronization if mutated concurrently
The heap is shared and garbage-collected, split into young and old generations so the GC can focus on short-lived objects.

A TestRun and its 2,000 step results stay on the heap until the run report is saved.

Shared · native memory

Metaspace

class structure, method bytecode, constant pools

Metaspace

Holds what the JVM knows about each loaded class — not your objects. Lives in native memory and grows until -XX:MaxMetaspaceSize (unlimited by default).

Grows abnormally with classloader leaks: repeated hot redeploys, runaway dynamic proxies, generated Groovy/script classes.

Metaspace stores class metadata in native memory; it only grows abnormally when classloaders leak.
Good to know

Code cache & direct memory

JIT output and NIO buffers — outside the heap

Off-heap memory adds up

Code cache holds JIT-compiled native code. Direct buffers (Netty, Kafka client, Mongo driver) are allocated outside the heap — -Xmx does not limit them.

Process memory = heap + metaspace + thread stacks + code cache + direct buffers. That's why a container can be OOMKilled while the heap looks healthy.

One frame per method call

A frame holds local variables, references, the operand stack and the return address. It's pushed on call and popped on return — no GC needed. Size per thread is set by -Xss; recursion that's too deep throws StackOverflowError.

The stack is private to a thread, holds method frames with locals and references, and is freed automatically on return.
Per thread

PC register

address of the bytecode instruction this thread runs next

Program counter

Each thread keeps its own pointer to the instruction it's executing (undefined while in a native method). It's what lets a thread resume exactly where it left off after a context switch.

Every thread needs its own PC so it can resume at the right instruction after the CPU switches threads.

The one-line rule

Primitives and references declared inside a method live in its stack frame. Objects — and every field inside them, even an int — live on the heap.

Good to know Escape analysis lets the JIT avoid heap allocation for objects that never leave a method.

Locals and references live in the thread's stack frame; the objects they point to live on the shared heap. A field of an object is on the heap, even if it's a primitive.
Strings

String pool

String pool

"staging" written twice → one pooled object. new String("staging") → a separate heap object every time. The pool moved from PermGen into the heap in Java 7, so unused pooled strings can be collected.

Literals are interned in the String pool, which lives in the heap since Java 7; new String() always creates a new object.

Collections

Minor vs full GC

Minor — young gen only, frequent, milliseconds.

Full — whole heap, rare, can take seconds.

Both pause the app (stop-the-world).

Minor, major, full

  • Minor: collects the young generation; live objects are copied to a survivor space or promoted
  • Major / Full: collects the old generation (full = whole heap); much slower
  • Stop-the-world: all application threads pause so the GC can move objects safely
Minor GCs clean the young generation often and quickly; full GCs clean the whole heap and cause the long pauses — frequent full GCs usually mean a leak or an undersized heap.
Collectors

G1 is the default

heap split into equal regions, aims for a pause target (200 ms)

Good to know · ZGC: sub-ms pauses

G1 and ZGC

G1 (default since Java 9) splits the heap into ~2,048 equal regions and collects the ones with most garbage first, aiming at -XX:MaxGCPauseMillis=200.

ZGC (generational since 21) does almost everything concurrently — pauses under 1 ms even on huge heaps.

We run G1 with defaults; I'd only switch to ZGC if p99 latency from GC pauses became a real problem.

The OutOfMemoryError family

read the message → know where to look
Most common
OutOfMemoryError: Java heap space

Causelive objects need more than -Xmx

Fixheap dump → who holds it? stream / paginate

Java heap space

Cause: a leak (objects still referenced) or a real load spike — e.g. loading 50,000 step results into one list.

Fix: heap dump → find what holds the memory; stream or paginate; raise -Xmx only if the load is genuine.

First I check whether it's a leak or real load: if Old gen doesn't drop after full GCs, it's a leak and the heap dump tells me who holds the objects.
Class metadata
OutOfMemoryError: Metaspace

Causetoo many classes loaded

Fixfind the leaking classloader; cap MaxMetaspaceSize

Metaspace

Cause: classloader leaks — hot redeploys, endless dynamic proxies, generated script classes.

Fix: find the leaking classloader in a heap dump; set MaxMetaspaceSize so it fails fast instead of eating the node.

Metaspace OOM means classes keep being loaded and never unloaded — almost always a classloader leak, not a heap problem.
GC thrashing
OutOfMemoryError: GC overhead limit exceeded

Cause98% of time in GC, <2% freed

Fixsame as heap space — it's the early warning

GC overhead limit exceeded

Cause: the heap is nearly full of live objects, so the GC runs constantly and frees almost nothing. The app crawls before it dies.

Fix: same as heap space — it's the early warning of the same problem.

It's the JVM giving up early: GC is running almost all the time but recovering almost nothing — treat it exactly like a heap-space OOM.
Threads
OutOfMemoryError: unable to create native thread

CauseOS refuses another thread — heap may be fine

Fixbounded pools; count threads in a thread dump

Unable to create native thread

Cause: thread leak — new Thread() per task, unbounded cached pool — hitting the OS/pod thread or memory limit. Heap may be nearly empty.

Fix: bounded thread pools; count threads in a thread dump.

It's not heap — the process can't get another OS thread. I'd take a thread dump, see which pool keeps growing, and bound it.

A per-test-case new Thread() in a 5,000-case suite.

Not an OOM — but asked together
java.lang.StackOverflowError

Causerecursion too deep (e.g. JSON back-references)

Fixbreak the cycle — -Xss only moves the limit

StackOverflowError

Cause: infinite or very deep recursion — classic: Jackson serializing Suite ↔ TestCase back-references forever.

Fix: break the cycle (DTO, @JsonManagedReference/@JsonBackReference) or make it iterative. Raising -Xss only moves the limit.

A StackOverflowError is a stack problem, not heap — one thread's frames ran out, almost always from unbounded recursion.
Kubernetes
OOMKilled · exit code 137

Causeprocess RSS > pod limit — no Java error at all

FixMaxRAMPercentage=75, check non-heap

OOMKilled

Cause: the kernel killed the process because heap + metaspace + stacks + direct buffers exceeded the container limit. Java never threw anything.

Fix: size the heap as a percentage (-XX:MaxRAMPercentage=75), leave headroom, check thread count and direct memory.

Exit 137 with no Java OOM means the container, not the heap, ran out — I check non-heap memory and leave ~25% headroom.

Flags you should know

tap flags to build the launch command
Command builder · fireflink-runner
Servers

Set -Xms = -Xmx

no heap resizing, predictable footprint

-Xms2g -Xmx2g

Why equal min and max?

The JVM won't spend time growing and shrinking the heap, and you find out at startup — not at 3 a.m. — whether the memory is really available.

On servers I set Xms equal to Xmx so the heap is committed up front and never resized under load.
Containers

Use MaxRAMPercentage

heap follows the pod limit — keep ~25% for non-heap

4 GB pod × 75% = 3 GB heap

Container-aware sizing

The JVM reads the cgroup memory limit (since 10 / 8u191). -XX:MaxRAMPercentage=75.0 gives a 3 GB heap in a 4 GB pod and scales automatically when the limit changes.

In Kubernetes I size the heap with MaxRAMPercentage around 75 instead of a hard Xmx, leaving room for metaspace, stacks and buffers.
Always on

Dump on OOM

HeapDumpOnOutOfMemoryError + a path on a mounted volume

-XX:HeapDumpPath=/dumps # PVC

Keep the evidence

Without a dump you can only guess. Write it to a persistent volume — a dump inside the container dies with the pod restart.

Every service runs with HeapDumpOnOutOfMemoryError and a HeapDumpPath on a mounted volume, so the first OOM is already diagnosable.

Leaks — and how to find one

a leak = objects you no longer need that are still reachable
Heap after each GC

Diagnose in 4 steps — tap each

Leak #1

Static cache

static Map that only grows

Fixbounded cache with TTL (Caffeine)

Static collections

Static fields are GC roots — everything they reference lives forever. A static Map<runId, RunResult> without eviction grows with every run.

Fix: a bounded cache with size/TTL (Caffeine), or don't cache at all.

The most common leak I've seen is an unbounded static map used as a cache — statics are GC roots, so nothing in it is ever collected.
Leak #2

ThreadLocal in pools

pool threads never die → values never go

Fixremove() in finally

ThreadLocal in a thread pool

Pool threads live forever, so a value set in a ThreadLocal stays reachable after the task ends — and leaks into the next task.

Fix: always remove() in finally.

ThreadLocals in pooled threads must be removed in a finally block, otherwise they leak memory and even data between requests.

Tenant context set per test run and never removed.

Leak #3

Listeners

registered per run, never removed

Fixunregister in cleanup

Listeners & callbacks

An object registered with a long-lived publisher stays reachable through it. Register per run, forget to unregister → every run's listener (and what it references) survives.

Fix: unregister in cleanup, or use weak references.

Anything you register with a long-lived object must be unregistered, or the registry keeps it alive forever.
Leak #4

Unclosed resources

streams, connections, browser sessions

Fixtry-with-resources · driver.quit()

Unclosed resources

Open streams, JDBC connections or WebDriver sessions hold buffers and native memory until closed.

Fix: try-with-resources; driver.quit() in finally.

Anything closeable goes in try-with-resources; leaked connections and sessions leak native memory, not just heap.

A WebDriver session not quit after a failed step keeps a browser process alive.
