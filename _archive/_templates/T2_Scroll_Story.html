01The map

Where things live inside one JVM process.

You run java -jar runner.jar. The OS gives the JVM one process, and inside it memory is split by who owns it and how long it lives.

Heap — every object you new. Shared by all threads, sized by -Xms/-Xmx, cleaned by the garbage collector.

Young generation = Eden + two Survivor spaces. New objects start in Eden. Most die young — a step result, a JSON string — and the GC is built on that bet.

Old generation — objects that survived several GCs: Spring beans, caches, connection pools.

Metaspace — class metadata: TestRun.class, method bytecode, Spring's generated proxies. It lives in native memory, replaced PermGen in Java 8, and grows unless you cap it.

Stack — one per thread. Frames hold local variables and references; the PC register points to the next instruction. Freed when the method returns — no GC involved.

Other native memory — JIT code cache, direct buffers (Netty, Mongo driver), GC bookkeeping. Not part of -Xmx, which matters in containers (chapter 5).

"The JVM has a shared heap for objects, split into young (Eden + survivors) and old generations, plus Metaspace in native memory for class metadata — it replaced PermGen in Java 8. Each thread gets its own stack of frames and a PC register. On top of that there's native memory for the code cache, direct buffers and thread stacks, which -Xmx doesn't cover."

02Stack vs heap

The question every interviewer opens with.

When a runner thread executes a step, it pushes a frame on its stack. Primitives and references sit in the frame; the objects they point to sit on the heap.

▶ Step through one method call
void runStep(Step step) {
    int retries = 0;                     // primitive → stack
    TestResult r = new TestResult(step); // ref → stack, object → heap
    r.setStatus("PASSED");               // literal from the String pool
    save(r);                             // new frame pushed, then popped
}                                        // frame popped → object unreachable

🎤 30-second interview answer

"Each thread has its own stack of frames holding primitives and references; it's freed automatically when a method returns, and if it gets too deep you get StackOverflowError. Objects always live on the shared heap and are reclaimed by the GC once nothing references them; running out gives OutOfMemoryError. Because the heap is shared, it's where thread-safety issues come from."

03Life of an object

Eden → Survivor → Old, and what "stop-the-world" means.

Every new TestResult() is allocated in Eden — fast, just a pointer bump in a thread-local buffer.

A suite with hundreds of steps fills Eden quickly…

…so a minor GC runs. It pauses the app threads briefly (stop-the-world), copies the few live objects into a Survivor space with age 1, and wipes Eden in one go.

Next minor GC: survivors are copied to the other Survivor space and their age goes up. The two spaces take turns — one is always empty.

Once an object's age reaches the tenuring threshold (up to 15) — or survivors overflow — it is promoted to the Old generation.

When Old fills up, the JVM needs a major / mixed GC, and in the worst case a full GC: the whole heap, the longest pauses. Frequent full GCs = your API latency spikes.

Good to knowG1 (default since Java 9) splits the heap into equal-size regions and collects the most garbage-filled ones first, aiming at a pause target (-XX:MaxGCPauseMillis, default 200 ms). ZGC does almost everything concurrently — sub-millisecond pauses even on huge heaps.
🎤 30-second interview answer

"New objects go to Eden. When Eden fills, a short stop-the-world minor GC copies live objects to a survivor space and clears Eden. Objects that survive enough GCs — the tenuring threshold, up to 15 — are promoted to the old generation. When old fills, we get mixed or full GCs with longer pauses. It works because most objects die young. G1 is the default collector; ZGC is the choice for very low pauses."

04When memory runs out

Same family name, five different problems.

OutOfMemoryError is only the surname — the message tells you which area ran out, and the fix is completely different for each. Click one:

🎤 30-second interview answer

"First I read the message. 'Java heap space' means too many live objects — usually a leak or an unbounded load — so I take a heap dump. 'GC overhead' is the same thing, detected earlier. 'Metaspace' means too many classes, often from dynamic proxies or classloader leaks. 'Unable to create native thread' is an OS or memory limit on threads — use bounded pools. StackOverflowError is runaway recursion."

"I set -Xms and -Xmx, or in containers MaxRAMPercentage around 70–75%, because the default is only 25% of the limit. And I always enable HeapDumpOnOutOfMemoryError with a dump path on a volume."

06Leaks & diagnosis

Java has a GC, and still leaks.

A leak in Java = objects you no longer need but still reference. The GC can't touch them, so they get promoted and pile up in Old gen — until full GCs run back-to-back.

🎤 30-second interview answer
"A Java leak is reachable but useless objects — typically static maps or caches without eviction, ThreadLocals not removed in thread pools, listeners never unregistered, or unclosed resources. I confirm it when old gen stays high after full GCs in jstat or the GC logs, take a heap dump with jcmd, and open it in MAT's dominator tree to find what retains the memory."
